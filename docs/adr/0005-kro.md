# 0005. kro for the platform layer, not Kratix and Backstage

**Status**: Proposed. Lesson 20 isn't written.

## Context

The last lesson turns the cluster into a product: a team asks for an
environment and gets one with the platform's defaults. Kratix Promises with a
Backstage portal was the first idea.

## Decision

kro: a `ResourceGraphDefinition` per offering, starting with "a team",
requested by committing one object to Git.

## Why

- Backstage is a framework you build an app from; real use means building
  your own image with plugins. That's application code, which this repo
  doesn't write.
- kro is run managed by EKS Capabilities, beside ACK and Argo CD; Kratix isn't
  EKS-native.
- It composes objects the cluster already has: namespace, quota, RBAC, a Flux
  tenant `Kustomization`, mesh enrolment, policy. Nothing new to operate.

## Costs

- No portal. The interface is Git and the CRD kro generates.
- ACK can't create real AWS resources locally, so offerings stay in-cluster.

## On EKS

kro through EKS Capabilities, with ACK so an offering can also create AWS
resources such as an S3 bucket or an IAM role. Check what EKS Capabilities
offers when the lesson is written.
