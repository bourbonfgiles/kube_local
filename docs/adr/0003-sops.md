# 0003. SOPS for secrets in Git

**Status**: Accepted. Built in lesson 5.

## Context

Lessons 3 and 4 left two Secrets made by hand: the TSIG key and the CA. Every
rebuild needed them again.

## Decision

SOPS with age, one key per holder, as a team would run it. Every file is
encrypted to my key, kept in GNOME Keyring and read through
`SOPS_AGE_KEY_CMD`, and to the cluster's key, which exists only in
`flux-system/sops-age`. No private key is shared or written to a file.

## Why

- Flux decrypts natively: no extra controller, nothing outside the cluster.
- Secrets are versioned and reviewed with the config that uses them.
- Works offline, with no cloud account.

## Costs

- The cluster's key is made by hand with each cluster, and every file is
  re-keyed to it with `sops updatekeys`. My key is what makes that possible,
  so it needs a backup outside the machine.
- Removing a person's key doesn't remove their access to history: their key
  still opens every earlier commit, so the values need rotating too.
- Rotating a value means re-encrypting and committing; rotating the key means
  re-encrypting every file.
- The ciphertext is in Git history for good.

## On EKS

SOPS with a KMS key, and kustomize-controller decrypting through an IAM role:
nothing copied by hand. The other common choice is External Secrets Operator
reading AWS Secrets Manager, so secrets never touch Git. That needs IAM for
pods, so revisit after lesson 18.
