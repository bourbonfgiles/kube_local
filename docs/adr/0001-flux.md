# 0001. Flux, not Argo CD

**Status**: Accepted. Built in lessons 2 and 6.

## Context

I ran Argo CD on AKS. This cluster exists to stay current on Kubernetes and
EKS, and a second GitOps tool widens that more than repeating the first.

## Decision

Flux, installed and upgraded by Flux Operator (`FluxInstance`).

## Why

- Helm charts become real Helm releases: `helm list`, `helm history` and
  hooks work. Argo CD renders the chart and keeps no release.
- Every change is a commit. The Flux Web UI shows and nudges; it can't create
  or edit an application.
- Flagger (lesson 10) and the image automation controllers (lesson 9) cover
  Argo Rollouts and Image Updater.
- Layers with `dependsOn` and per-cluster `postBuild` variables keep one base
  for every cluster (lessons 2 and 3).

## Costs

- No app-centric UI to work from; the CLI and sofka do that job.
- HelmRelease drift is ignored unless `driftDetection` is on.
- Polling on intervals, not watching: changes land at `interval`, or on
  `flux reconcile`.

## On EKS

Flux isn't an EKS add-on; `flux bootstrap` or Flux Operator installs it as
here. EKS Capabilities offers Argo CD managed by AWS, so a shop on that runs
Argo. The translation is in lesson 2's and lesson 6's "Coming from Argo CD".
